작업을 커밋합니다. 사용자는 커밋 메시지를 직접 쓰지 않습니다. **당신이 대신 씁니다.**

## 1. 브랜치 확인

```bash
git symbolic-ref --short -q HEAD
```

`main` / `master` / `develop` 이면 **커밋하지 말고** 이렇게 안내하세요.
(이 셋은 보호 브랜치라 직접 커밋할 수 없습니다. 훅이 실제로 막습니다.)

> 지금 `develop` 브랜치라 바로 저장할 수 없어요.
> `/start <무슨 작업인지>` 로 작업 브랜치를 먼저 만들어 주세요.

## 2. 검사 통과시키기

> 검사 명령(테스트·린트)은 서버 뼈대(#4)에서 도구를 정하면 여기에 추가합니다. (CLAUDE.md 5장)

지금은 CLAUDE.md 5장의 확인을 합니다.

- 훅(`.githooks/`, `.claude/hooks/`)을 고쳤으면 직접 실행해서 확인
- `db/schema.sql` 을 고쳤으면 "Neon 에서 실행 확인" 을 사용자에게 부탁

실패하면 **커밋하지 말고** 원인을 고칩니다. 고쳐도 안 되면 에러 메시지를 그대로 보여주고 물어봅니다.

## 3. 무엇이 바뀌었는지 읽기

```bash
git status --short && git diff
```

**`.env` 가 목록에 있으면 절대 add 하지 마세요.** (git 훅도 막습니다)

## 4. 커밋을 나눌지 판단

성격이 다른 변경이 섞여 있으면 **커밋을 나눕니다.**
(예: 계획 API 추가 + 스키마 컬럼 수정 → 커밋 2개, 파일을 나눠서 `git add`)

## 5. 커밋

파일을 명시해서 add 하세요. `git add .` 는 쓰지 마세요.

```bash
git add <바뀐 파일들>
git commit -m "$(cat <<'MSG'
feat: 날짜별 공부 계획 목록 API 추가

날짜 형식이 틀리면 400, 계획이 없으면 빈 배열을 돌려줍니다.

Refs: #11
Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
MSG
)"
```

메시지 규칙:

- 제목: `타입: 한국어로 무엇을 했는지` (50자 이내, 마침표 없음)
- 타입: `feat` `fix` `refactor` `style` `docs` `chore` `test`
- 본문: 왜 그렇게 했는지 필요할 때만 2~3줄
- 관련 이슈가 있으면 `Refs: #12`
